# 配置失误的关键症结：知识库同步滞后 ≥20 分钟

## 我的判断

数据是 2026-09-01 至 09-07 的 1,297 条实施查询，其中 1,252 条有现场结果回传，45 条未回传（3.47%）。有回传样本里 161 次故障，整体故障率 **12.86%**。

**看到的第一个事实**：故障率对「知识库同步滞后」不是渐变，而是断层。滞后 = `query_time − kb_synced_at`（统一转 UTC 计算）。

| 同步滞后 | 查询数 | 故障数 | 故障率 | 占全部故障 |
|---|---:|---:|---:|---:|
| < 20 分钟 | 925 | 30 | **3.24%** | 18.63% |
| ≥ 20 分钟 | 327 | 131 | **40.06%** | **81.37%** |

滞后 0–18 分钟都有样本，**19–21 分钟一条样本都没有**，22 分钟起故障率直接跳到 44% 以上。阈值取 20 分钟，是落在这段数据空档里，不是拟合出来的精确点；取 19、20、21 分钟结果完全相同。

**排除两个看起来更直觉的解释**：

- 不是检索置信度。在新鲜组内部，`match_margin ≤4`（最紧张）故障率 5.03%，`>16` 是 2.85%，中间还出现过 0.89%，没有单调关系。全样本上 margin 与故障的相关系数只有 −0.02。
- 不是推理速度。新鲜组内推理 `>63ms` 的故障率反而最低（1.69%）。整体上推理慢的查询故障更多，是因为过期查询本身更慢（中位 59ms vs 52ms）——推理时长是伴生现象，不是杠杆。

**团队/类别差异主要是「暴露在过期知识下」的比例不同**。分层后，新鲜组五个团队故障率 1.08%–7.89%，过期组除华中外都在 43.1%–51.9%：

| 团队 | 查询 | 过期占比 | 新鲜组故障率 | 过期组故障率 |
|---|---:|---:|---:|---:|
| 华东机床组 | 231 | 22.5% | 2.23% | 50.00% |
| 华中产线组 | 266 | 28.6% | 7.89% | **9.21%** |
| 华北重工组 | 247 | 25.1% | 2.16% | 51.61% |
| 华南电子组 | 265 | 29.8% | 1.08% | 51.90% |
| 西南汽车组 | 243 | 23.9% | 2.70% | 43.10% |

**根部问题是助手在生成建议时没有校验知识库新鲜度**：当同步滞后 ≥20 分钟，一线仍在采纳基于过期文档的参数配置建议，故障率从 3.2% 抬到 40.1%。这是当前数据里最大、也最可直接干预的症结。这是观察性数据，不能证明因果；但断层、剂量关系、以及分层后团队差异基本被「是否过期」解释，三者一致指向它。

**一个必须保留的例外**：华中产线组 76 条过期查询只有 7 次故障（9.21%），和其他团队同条件下的 43%–52% 完全不同，且滞后分布与其他团队相当（中位 45 分钟）。数据里没有他们的操作细节，不能归因；这是最值得现场访谈的一条线索，而不是可以忽略的噪声。

## 做了什么

1. 用「同步滞后 ≥20 分钟」定义过期查询；时间统一按 UTC 计算滞后，展示用 Asia/Shanghai。
2. 故障率只用 1,252 条有回传样本；45 条未回传单列，不当作成功、不静默丢弃。
3. 做分层检验，排除团队、业务类别、匹配裕度、推理时长作为主因。
4. 建立阈值—工时模型：每次故障 90 分钟、每次预警转人工 12 分钟（任务书口径），扫描 10–40 分钟阈值。
5. 给出改进策略与优先级：**回答前做新鲜度门禁**（≥20 分钟先强制同步或阻断），做不到门禁就转人工；**不要**把资源投在收紧 margin 或推理加速；优先治理过期故障率最高的「报警联动规则」；访谈华中。

## 怎么证明有用

**成本对比（有回传的 1,252 条）**

- 不干预：161 次故障 × 90 = **14,490 分钟**
- 滞后 ≥20 分钟一律预警转人工：327 次预警 × 12 + 剩余 30 次故障 × 90 = 3,924 + 2,700 = **6,624 分钟**
- 节省 **7,866 分钟（54.3%）**，同时覆盖 **131/161 = 81.37%** 的故障
- 运行负担：全部 1,297 条里 337 次预警，5 个团队 × 7 天 ≈ **9.6 次/队/天**

**阈值不是拍脑袋**：10 分钟要 768 次预警、总成本 10,566；15 分钟 541 次、8,472；18 分钟 388 次、7,266；**20/22 分钟 327 次、6,624（最低）**；25 分钟 306 次、7,272；30 分钟 274 次、8,148。阈值再低，预警成本吃掉收益；再高，漏掉的故障代价更大。

**假设转人工不是万能的**：如果被识别出的故障只有 80% 被真正拦住，仍省 5,508 分钟（38.0%）；只有 60% 被拦住，仍省 3,150 分钟（21.7%）。即使效果打六折，策略仍是正收益。

**证据图**

- `results/figures/fail_by_lag.png`：故障率随滞后的断层，20 分钟处竖线。
- `results/figures/fail_by_team_strata.png`：分层后团队差异，同一条柱是新鲜、另一条是过期。
- `results/figures/cost_curve.png`：阈值—总工时曲线，20 分钟为最低点。

## 复现

```bash
python -m venv .venv
pip install -r requirements.txt
python analyze_faults.py --data assistant_query_logs.csv --out results
```

输出 `results/business.json` 与三张图。关键字段：

- `overall`：故障数、故障率、未回传占比
- `lag.fresh` / `lag.stale`：两组查询数、故障数、故障率、故障占比
- `confounders`：分层后的团队/类别/margin/推理时长
- `strategy.thresholds`：每个阈值的预警数、覆盖故障数、总成本、节省
- `strategy.recommended`：推荐阈值的运行负担与三种拦截率下的敏感性

## 局限

- 观察性数据，只有 7 天、一个产品；不能证明「过期导致故障」，只能证明强关联与可干预性。上线前应做一次对照：对 ≥20 分钟的查询随机一半触发强制同步，比较故障率。
- 45 条未回传（35 条新鲜、10 条过期）按缺失处理；如果它们的故障率与已回传样本不同，绝对数字会变，但过期组占 81% 故障的结论需要极端偏差才会翻转。
- 12/90 分钟来自任务书口径，不是现场实测；成本结论只覆盖工时，不含返工、客户信任等。
- 20 分钟阈值落在 19–21 分钟的无样本空档；运营上取 19–21 任意值等价，需要后续数据校准。
- 华中的低故障率无法由现有字段解释，是待访谈项，不是已解释结论。
