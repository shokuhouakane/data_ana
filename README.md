# 配置失误的关键症结：知识库同步滞后 ≥20 分钟

## 我的判断

原始文件 1,297 行，但 `query_id` 是任务书定义的单据唯一流水号，其中 **62 条是整行重复**（`query_id` 也重复）。按 `query_id` 保留第一条后是 1,235 条查询；其中 1,191 条有现场结果回传，44 条未回传（3.56%），152 次故障，整体故障率 **12.76%**。

去重前后结论方向一致：未去重时是 1,252 条有回传、161 次故障（12.86%），过期组占故障 81.37%；去重后为 80.92%。本文全部使用去重后的 1,235 条。

**看到的第一个事实**：故障率对「知识库同步滞后」不是渐变，而是断层。滞后 = `query_time − kb_synced_at`（统一转 UTC 计算）。

| 同步滞后 | 查询数 | 故障数 | 故障率 | 占全部故障 |
|---|---:|---:|---:|---:|
| < 20 分钟 | 881 | 29 | **3.29%** | 19.08% |
| ≥ 20 分钟 | 310 | 123 | **39.68%** | **80.92%** |

滞后 0–18 分钟都有样本，**19–21 分钟一条样本都没有**；18 分钟的故障率是 1.72%（n=58），22 分钟是 37.5%（n=8），23–25 分钟为 40.0%–57.1%。阈值取 20 分钟，是落在这段数据空档里，不是拟合出来的精确点；取 19、20、21 分钟结果完全相同。滞后与故障的相关系数是 **0.445**。

**排除两个看起来更直觉的解释**：

- 不是检索置信度。在新鲜组内部，`match_margin ≤4`（最紧张）故障率 5.19%，`>16` 是 2.77%，中间 9–12 档还低到 0.93%，没有单调关系；全样本 margin 与故障的相关系数只有 **−0.029**。
- 不是推理速度。新鲜组内推理 `>63ms` 的故障率反而最低（1.78%）。整体上推理慢的查询故障更多，是因为过期查询本身更慢（中位 58ms vs 52ms）——推理时长是伴生现象，不是杠杆。

**团队/类别差异主要是「暴露在过期知识下」的比例不同**。分层后，新鲜组五个团队故障率 1.12%–7.87%，过期组除华中外都在 44.4%–50.9%：

| 团队 | 查询 | 过期占比 | 新鲜组故障率 | 过期组故障率 |
|---|---:|---:|---:|---:|
| 华东机床组 | 222 | 21.6% | 2.30% | 50.00% |
| 华中产线组 | 252 | 29.4% | 7.87% | **9.46%** |
| 华北重工组 | 233 | 25.3% | 2.30% | 50.85% |
| 华南电子组 | 253 | 29.6% | 1.12% | 50.67% |
| 西南汽车组 | 231 | 23.4% | 2.82% | 44.44% |

**根部问题是助手在生成建议时没有校验知识库新鲜度**：当同步滞后 ≥20 分钟，一线仍在采纳基于过期文档的参数配置建议，故障率从 3.3% 抬到 39.7%。这是当前数据里最大、也最可直接干预的症结。这是观察性数据，不能证明因果；但断层、剂量关系、以及分层后团队差异基本被「是否过期」解释，三者一致指向它。

**一个必须保留的例外**：华中产线组 74 条过期查询只有 7 次故障（9.46%），过期查询的滞后中位数 44 分钟（与其他团队同量级），却远低于其他团队同条件下的 44%–51%。数据里没有他们的操作细节，不能归因；这是最值得现场访谈的一条线索，而不是可以忽略的噪声。

## 做了什么

1. **先去重**：按任务书定义的唯一键 `query_id` 保留第一条，剔除了 62 条整行重复；原始行数、去重数和规则都写进 `results/business.json` 的 `meta`。
2. 用「同步滞后 ≥20 分钟」定义过期查询；时间统一按 UTC 计算滞后，展示用 Asia/Shanghai。
3. 故障率只用 1,191 条有回传样本；44 条未回传单列（35 条新鲜、9 条过期），不当作成功、不静默丢弃。
4. 做分层检验，排除团队、业务类别、匹配裕度、推理时长作为主因。
5. 建立阈值—工时模型：每次故障 90 分钟、每次预警转人工 12 分钟（任务书口径）；**预警发生在查询时，未回传查询同样会触发预警**，所以预警数按全部 1,235 条计算，故障只按有回传样本计算。
6. 给出改进策略与优先级：**回答前做新鲜度门禁**（≥20 分钟先强制同步或阻断），做不到门禁就转人工；**不要**把资源投在收紧 margin 或推理加速；优先治理过期故障率最高的「报警联动规则」（过期组 53.12%）；访谈华中。

## 怎么证明有用

**成本对比（1,235 条查询、1,191 条有回传）**

- 不干预：152 次故障 × 90 = **13,680 分钟**
- 滞后 ≥20 分钟一律预警转人工：319 次预警 × 12 + 剩余 29 次故障 × 90 = 3,828 + 2,610 = **6,438 分钟**
- 节省 **7,242 分钟（52.9%）**，同时覆盖 **123/152 = 80.92%** 的故障
- 运行负担：319 次预警，5 个团队 × 7 天 ≈ **9.1 次/队/天**

**阈值不是拍脑袋**：10 分钟要 754 次预警、总成本 10,398；15 分钟 532 次、8,274；18 分钟 379 次、7,068；**20/22 分钟 319 次、6,438（最低）**；25 分钟 298 次、6,996；30 分钟 268 次、7,806。阈值再低，预警成本吃掉收益；再高，漏掉的故障代价更大。

**假设转人工不是万能的**：如果被识别出的故障只有 80% 被真正拦住，仍省 5,028 分钟（36.8%）；只有 60% 被拦住，仍省 2,814 分钟（20.6%）。即使效果打六折，策略仍是正收益。

**为什么这比优化检索/推理更划算**：新鲜组的故障率已经接近地板（3.29%），且组内 margin 与推理时长都没有可用梯度；过期组 39.68% 的故障率才是杠杆。把资源投在模型侧，最多改善新鲜组那 29 次故障中的很小一部分。

**证据图**

- `results/figures/fail_by_lag.png`：故障率随滞后的断层，20 分钟处竖线。
- `results/figures/fail_by_team_strata.png`：分层后团队差异，同一团队两根柱分别是新鲜与过期。
- `results/figures/cost_curve.png`：阈值—总工时曲线，20 分钟为最低点。

所有数字的机器可读来源是 `results/business.json`，字段与本文一一对应。

## 复现

```bash
python -m venv .venv
pip install -r requirements.txt
python analyze_faults.py --data assistant_query_logs.csv --out results
```

输出 `results/business.json` 与三张图。关键字段：

- `meta`：原始行数、去重数、去重规则、**去重前对照指标**、有回传/未回传数
- `overall`：故障数、故障率、未回传占比
- `lag.fresh` / `lag.stale`：两组查询数、故障数、故障率、故障占比
- `lag.exact_minutes_15_25`：18 分钟与 22–25 分钟的逐分钟样本与故障率
- `lag.unlabeled_split`：未回传中新鲜/过期各多少
- `correlations`：滞后、margin、推理时长与故障的相关系数
- `confounders`：分层后的团队/类别/margin/推理时长
- `strategy.thresholds`：每个阈值的预警数、覆盖故障数、总成本、节省
- `strategy.recommended`：推荐阈值的运行负担与三种拦截率下的敏感性

## 局限

- 观察性数据，只有 7 天、一个产品；不能证明「过期导致故障」，只能证明强关联与可干预性。上线前应做一次对照：对 ≥20 分钟的查询随机一半触发强制同步，比较故障率。
- 62 条重复按 `query_id` 剔除。如果它们其实代表真实重复查询而非回传重复，绝对故障数会略变（未去重时 12.86% vs 去重后 12.76%），但不改变过期组占约 81% 故障的结论。
- 44 条未回传（35 条新鲜、9 条过期）按缺失处理；如果它们的故障率与已回传样本不同，绝对数字会变，但结论需要极端偏差才会翻转。
- 12/90 分钟来自任务书口径，不是现场实测；成本结论只覆盖工时，不含返工、客户信任等。
- 20 分钟阈值落在 19–21 分钟的无样本空档；运营上取 19–21 任意值等价，需要后续数据校准。
- 华中的低故障率无法由现有字段解释，是待访谈项，不是已解释结论。

## 数据说明

- `assistant_query_logs.csv`：任务方发放的正式数据，原样提交，未做任何修改；去重只发生在分析脚本内存中，并显式记录在 `meta`。
- `tests/fixtures/synthetic_orders.csv`：**合成测试数据**，仅用于验证通用管线，不参与本文任何结论。
